# Risks — agencyBRIDGE

| ID | Risk | Impact | Likelihood | Mitigation | Status |
|---|---|---|---|---|---|
| R-001 | Authentication was client-side only: `roleContext.tsx` compared a SHA-256 digest of the submitted password against a digest compiled into the bundle, and the "session" was a `localStorage` value the user could type. | Critical | Certain (it was not a control) | Closed by D-010. Credentials are verified server-side (scrypt, D-012), sessions are random tokens stored as digests and delivered in an HttpOnly cookie, and every route resolves identity from that cookie. The digest table and the client-side session are gone. Verified end to end — see EV-010. | **Closed** |
| R-002 | `clearAuditLog` enforced an admin role in the browser, which any user could satisfy. | Medium | High | Closed by D-013. The operation no longer exists: the trail is append-only in Postgres and there is no endpoint that removes an entry. | **Closed** |
| R-003 | Marketing claims "audit logging meeting CMS 42 CFR requirements". | High | Medium | Materially advanced by D-013: the log is now server-side, append-only, hashed where the client cannot reach it, and verified by the server. What remains unmet is the rest of the regulation — retention guarantees, defined access review, backup and recovery, and an independent time source. The claim is closer to true but is not yet earned. Either complete those controls or soften the copy. | Open — reduced |
| R-004 | Retention cap discards the oldest entries at 2,000. A client-side chain cannot prove its own head existed. | Medium | Medium | `persist()` records the `prevHash` the retained head must carry, and verification checks it, so head deletion is reported as tampering rather than rollover — at any point in the log's life. An attacker with devtools can still edit the boundary key alongside the log; only server-side append-only storage closes that. | Mitigated |
| R-005 | Test coverage is narrow and now spans two layers: the security-critical server modules are covered (`scope`, `password`, `permissions`, `auditChain`), but no test exercises an API handler end to end, and none of the 26 page components has a test. Regressions in request handling or UI logic would not be caught. | Medium | Medium | 132 tests cover the security- and money-critical logic. The gap that matters most is handler-level: authorization is proven at the unit level and by manual exercise (EV-010), not by an automated integration suite. | Open |
| R-006 | Landing hero and OG/Twitter share images are hot-linked from `vibe.filesafe.space`, a third-party CDN outside the project's control, with no provenance or licence record. | Medium | Medium | Re-host as owned assets under `public/` and record provenance in `brand/BRAND-PACKAGE.md`. | Open |
| R-007 | Adversarial review has covered `src/lib` logic only. The 26 page components — including untrusted-input surfaces such as the knowledge base and email campaign builder — have not been red-teamed. | Medium | Medium | Schedule a page-layer red-team pass; treat any finding as a regression-test target. | Open |
| R-008 | agencyBRIDGE is not listed in `build-contract-os/registry/PROJECT-REGISTRY.yaml`, so the portfolio control plane does not know it is governed. | Low | Certain | Registry entry must be added upstream; this session has read-only access to that repo (D-002). | Open — needs upstream write |
| R-009 | Contract and repository drift: the local working branch was stale against `origin/main` at session start. | Low | Medium | Reconcile on every agent entry; `RESUME.md` protocol followed and branch reset before any edit. | Mitigated |
| R-010 | Two tabs logging at the same moment each read-modify-write the whole log in `localStorage`, so one tab's entry could be silently overwritten. | Medium | Low | Closed by D-013. There is no client-side chain to race on. Concurrent appends now contend on `unique (tenant_id, seq)` in Postgres, which turns a race into a failed insert and a retry rather than a lost entry. | **Closed** |
| R-011 | The demo tenant's audit chain grows without bound: every visitor's session appends to it, and nothing trims it. Verification walks the whole chain in one query, so both the table and the verify request degrade over time. | Low | High (given traffic) | Bounded for now by the demo being the only public tenant and by the `limit` on reads; verification is the unbounded one. Add a retention window that **records the boundary hash it trims to**, so truncation stays distinguishable from deletion (the property `verifyAudit` currently relies on `seq = 1` for). | Open |
| R-012 | `DATABASE_URL` must be set by hand in the Vercel project. It is not in the repository and cannot be set from this environment, so a fresh deployment has no database until an operator adds it. | Medium | Certain until done | The API answers 503 `not_configured` with the exact remedy rather than a generic 500, so the failure is legible rather than mysterious. Setting the variable is a manual step — see README. | Open — needs operator action |
| R-013 | Demo sessions are unauthenticated in the ordinary sense: anyone may open one, and each creates a session row and audit entries. There is no rate limit on `/api/auth/demo`. | Low | Medium | Password login is throttled per email and per IP; the demo gate is not. Cheap to abuse into table growth, though it exposes no data beyond the synthetic book. Add a per-IP ceiling on demo session creation. | Open |
| R-014 | `POST /api/audit` accepts arbitrary action, entity and details from any authenticated caller, so the chain can be padded with events that never happened. | Medium | Medium | Bounded: actor, session and IP are taken from the session, category and severity are validated against a fixed vocabulary, and entries are additive — the trail can be padded but not falsified as to who acted, and nothing existing can be altered. The real fix is to emit events from the server-side operation handlers rather than accept them from the client. | Open |
| R-015 | A batch of audit appends is not one transaction. If the response is lost after some entries commit, the client retries the whole batch and duplicates them. | Low | Low | The transport retries only on transient failures, and duplicates are visible rather than silent. Needs client-generated idempotency keys. | Open |
| R-016 | In `client-update` the row is written and the audit entry appended as two statements. A failure between them leaves a committed change with no audit record. | Medium | Low | The audit append is not best-effort here — it throws, so the caller sees a 500 rather than a silent gap — but the write is already committed. Needs one transaction or a durable outbox. | Open |
| R-017 | Login throttling reads the failure count and inserts the failure as two statements, so concurrent attempts can all pass the check before any of them records. | Medium | Low | Bounds a burst rather than a sustained attack; scrypt at ~470ms per attempt limits throughput regardless. Needs an atomic counter or advisory lock. | Open |
| R-018 | Every demo visitor's IP and user agent is appended to the shared demo tenant's audit chain, which any demo visitor may read as the auditor role. | Medium | High | Real personal data on a public endpoint. Redact network metadata for demo tenants, or isolate demo audit data per visitor. | Open |
| R-019 | The Security page's CSV export serialises only the 500 loaded rows, so a longer trail exports silently truncated. | Low | Medium | Label the export as limited, or add a server-side paginated export. | Open |
| R-020 | The database does not enforce the append-only audit trail: the API's role can update or delete `audit_events` and `audit_heads`. | Medium | Low | The chain makes tampering **detectable**, which is what it claims, and detection is what the Security page reports. Making it impossible needs a restricted writer role or a security-definer function. | Open |
| R-021 | Two browser tabs share one outbox and flush it independently, so an entry can be sent twice or lost. | Low | Medium | Duplicates are visible in the trail rather than silent. Needs a lock/claim protocol or a per-tab outbox. | Open |
| R-022 | The audit row and its head marker are two statements. A failure between them leaves a stale marker, and verification then reports tampering that did not happen. | Medium | Low | The marker only moves forward, so the window is small and self-healing on the next append; a false alarm is still a false alarm. Needs one transaction. | Open |
| R-023 | Verification reads the entries and the head marker in separate queries, so an append landing between them can make a healthy chain look truncated. | Low | Medium | Transient and clears on the next check. Needs a consistent read. | Open |
| R-024 | Expired and revoked sessions, and every login attempt, are retained forever — including IP and user agent. | Medium | Certain over time | Unbounded growth and unnecessary retention of identifying data. Needs a scheduled purge. | Open |
| R-025 | The session cookie has no `__Host-` prefix, so a sibling subdomain that can set cookies on the parent domain could plant a duplicate `ab_session`. | Low | Low | Requires control of a sibling subdomain. `__Host-` plus rejecting duplicate cookie names closes it. | Open |
| R-026 | A mutation with no `Origin` header skips the same-origin check. | Low | Low | Deliberate: a browser always sets `Origin` on a cross-site mutation, and a non-browser client has no ambient cookie. Recorded because it is an assumption, not a proof. | Accepted |
| R-027 | Passwords are normalised NFKC, which folds compatibility characters and makes a few visually distinct passwords aliases. | Low | Low | Small entropy cost against a real cross-keyboard benefit. Changing to NFC now would invalidate existing hashes. | Accepted |
| R-028 | `requireRoute` is defined and never called. | Low | Certain | Endpoints are scope-gated, not route-gated, so it may be dead. Keep it and wire it, or delete it. | Open |
| R-029 | Client notes over 2,000 characters are truncated silently and the write returns 200. | Low | Low | The caller is not told their text was cut. Should reject instead. | Open |
| R-030 | The route-coverage test parses `App.tsx` with a regex, so a route declared in another form is silently skipped by the guard. | Low | Medium | The guard is better than nothing and worse than a shared export. Export the route table from a module both the app and the test import. | Open |
| R-031 | Audit entries still queued at sign-out are discarded even when the revoke never reached the server, so a sign-out that fails offline loses them permanently. The same applies to entries beyond one request's worth, and to entries on the wire in an append that then fails. | Low | Low | Deliberate over the alternative: entries name no actor, so one left over from a failed sign-out and delivered under the next session would be filed against the wrong person, and a gap is a better failure than a misattribution. The real fix is to bind each queued entry to the session id that produced it and have the server reject entries whose session does not match the caller's, after which they could be retained safely. | Open |
| R-032 | Sign-out clears the session cookie when the revoke fails. The header clears whatever cookie the browser holds when the response lands, so a sign-in inside that window loses its brand-new cookie. | Low | Low | Needs both a failed revoke and a concurrent sign-in. The alternative — never clearing — would leave a caller signed in against a token that may still authenticate, which is the worse failure. Binding the clear to a specific cookie value is not something cookies support; a fix needs the client to re-assert its session after a failed sign-out. | Open |
